White Paper Brief · Two-Phase Plan

S_general plan: MATH + APPS + LogiQA

Build three SEAL-style calibration vectors (1,000 questions each), then one pooled general vector — in two phases. Phase 1: run out every dataset and pool all boundary vectors, no balancing. Phase 2: rebuild by equalizing boundary vectors across domains. Code domain is APPS via v_code-SEAL — not MBPP.

Phase 1 (no balancing): generate 1,000 questions per domain (MATH, APPS, LogiQA) → extract layer-20 \n\n boundary vectors → pool all of them as-is → S_general = mean(check+switch) − mean(other).

Phase 2 (balancing): count boundary vectors per domain → set budget = min(n_math, n_apps, n_logic) → subsample each domain to that budget → rebuild S_general and compare against Phase 1.
1,000 Questions per domain Run out the full 500+500 on MATH, APPS, and LogiQA.
2 Phases Phase 1: pool everything. Phase 2: equal boundary budget.

Trace vs boundary vector vs activation

1 · Broadest
Activation

Model’s internal vector at one token, one layer (~1536-d at layer 20). Every token has one.

2 · Whole attempt
Trace

One full problem attempt (prompt + CoT). 500 correct + 500 incorrect = 1000 traces per domain.

3 · What SEAL keeps
Boundary vector

Layer-20 activation at a \n\n thought boundary. One trace → many boundary vectors. These are what Stage 3 averages.

activation      = one vector at one token, one layer
boundary vector = one activation, only at a \n\n position
trace          = one problem response, containing many boundary vectors 
Trace (one problem):
  <think>
  First I read the passage...      ← many tokens
  \n\n                             ← KEEP → boundary vector #1
  Wait, let me check...            ← many tokens
  \n\n                             ← KEEP → boundary vector #2
  Alternatively...                 ← many tokens
  \n\n                             ← KEEP → boundary vector #3
  </think>

labels: check = reflection · switch = transition · other = execution

Phase 1 — Run everything, pool all boundary vectors (no balancing)

Goal: get a working S_general end-to-end as fast as possible. Generate all 1,000 questions per domain, extract every \n\n boundary vector, and pool them as-is. Whatever domain has more thoughts contributes more votes — that is fine for the first pass and gives a baseline to measure Phase 2 against.

Steps

  1. Generate 500 correct + 500 incorrect traces per domain (MATH, APPS, LogiQA) — run out the full 1,000.
  2. Extract hidden.pt for each (correct + incorrect dirs).
  3. Cut at \n\n → boundary vectors, tag with each domain’s keyword set (check / switch / other).
  4. Pool all of them — concatenate every boundary vector from all three domains, no subsampling.
  5. Build S_general = mean(check + switch) − mean(other) over the full pool.

Still balance within each domain

Keep ~50/50 correct vs incorrect when filling the 500+500 pools. That is SEAL’s sampling control and applies in both phases. Phase 1 only skips the cross-domain balancing.

Phase 2 — Equalize boundary vectors across domains

Why: Stage 3 averages boundary vectors. In Phase 1, math’s longer CoTs cast more \n\n votes, so it dominates the average. Phase 2 syncs the votes so no single domain drives S_general, then compares against the Phase 1 vector.
You sync…Balances…Use for S_general?
Traces # problems per domain ❌ Indirect — long CoTs still dominate
Boundary vectors # \n\n states per domain ✅ Direct — inputs to mean(...)
All-token activations every token ❌ Not used by SEAL extraction

Boundary budget · Count → min(...) → subsample

  1. Reuse the same hidden.pt from Phase 1 (no regeneration).
  2. Count — for each domain, sum step.shape[0] over all traces in both dirs (= total \n\n boundary vectors).
  3. Set budget = min(n_math, n_apps, n_logic) — the equal amount, always the scarcest domain.
  4. Subsample — from each domain, randomly keep exactly budget boundary vectors (seeded RNG), keeping each vector’s check/switch/other label.
  5. Pool + build — concatenate the three equal sets, then S = mean(check+switch) − mean(other).
  6. Compare — cosine similarity and eval matrix vs the Phase 1 vector.

Why not stop at equal traces?

Example: 500+500 each, but math averages 40 thoughts/trace while APPS averages 12 → math still casts most votes. Equal traces looks fair on disk; equal boundary vectors is fair in the math that creates S_general.

Three keyword sets · tag per domain, then mix

Design choice: use a separate keyword list for each domain (math / code / logic). Filtering and tagging happen before the mixture, so keywords stay domain-local. The mixture only equalizes how many already-tagged boundary vectors each domain contributes.
DomainKeyword set at selection timeWhen applied
MATH math set Stage 2 · before mixture
APPS code set Stage 2 · before mixture
LogiQA logic set Stage 2 · before mixture

Order of operations

Per domain (separately)

  1. Generate traces
  2. Cut at \n\n → candidate boundary vectors
  3. Tag with that domain’s keywords → check / switch / other
  4. Later: subsample to budget

Then once

  1. Mix the already-tagged vectors (equal boundary counts)
  2. mean(check+switch) − mean(other) → S_general

What the mixture sees

Not raw traces — already classified boundary vectors:

MATH:  {check, switch, other}   tagged with math keywords
APPS:  {check, switch, other}   tagged with code keywords
LOGIC: {check, switch, other}   tagged with logic keywords
        │
        ▼  subsample each domain to budget
        │
        ▼  pool
S_general = mean(all check+switch) − mean(all other)

Why this is coherent

You’re not asking one keyword list to work on all text. Each domain’s detector picks its own over-thinking vs execution boundaries; then each domain gets equal votes in the average.

Domain-appropriate filters first → equal-count mixture second. The mixture does not re-run keywords. Syncing boundary-vector counts balances votes; using three keyword sets intentionally does not sync the labeling rule.

Appendix

A · Shared-keyword ablation (optional)

A sanity-check experiment — not part of the main build. Change one thing and see if results move.

RunKeyword ruleEverything else
Headline (main plan) MATH→math, APPS→code, LogiQA→logic 500+500, equal boundary budget, layer 20
Control (ablation) One shared list for all three (e.g. all code, or union) Same mixture, same budget, same layer

Why bother?

With 3 keyword sets, two things are mixed into S_general:

  1. Real shared “stop over-thinking” signal across domains
  2. Differences from using different taggers

The control asks: how much did (2) matter?

If control ≈ headline…Meaning
Recovery / geometry barely change Domain-specific keywords didn’t drive the result — 3-set design is fine
Numbers move a lot A big chunk of the effect was “we labeled domains differently,” not “calibration is shared”

Concrete example

Still ~80% → keyword choice wasn’t load-bearing. Drops to ~40% or flips geometry → keyword mismatch was doing real work; report that.

Do you need it?

No for the first run. It’s optional follow-up so reviewers can’t say “your general vector only looks general because each domain used a different filter.”

Main plan: 3 keyword sets. Optional ablation: one shared set, same mixture, compare.
